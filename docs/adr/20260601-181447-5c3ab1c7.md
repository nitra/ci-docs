## AML vs DBML для цього кейсу

|                      | **AML**                           | **DBML**                             |
| -------------------- | --------------------------------- | ------------------------------------ |
| Рендер у GitHub      | Ні (plain text)                   | Ні                                   |
| Підтримка в Azimutt  | Нативна (рідний формат)           | Так (імпорт)                         |
| Підтримка ще десь    | Тільки Azimutt                    | dbdocs.io, DbDiagram, Prisma-тулси   |
| SQL → X через npx    | `npx @azimutt/cli@latest convert` | `npx @dbml/cli sql2dbml`             |
| SVG без Chromium     | Ні                                | `npx @softwaretechnik/dbml-renderer` |
| Azimutt без конверт. | **Напряму імпортує ваш `.sql`**   | Теж імпортує                         |

**Ключовий момент:** Azimutt вже зараз читає ваш `*.sql` напряму (drag-n-drop або `azimutt gateway`). Тобто генерація `.aml` у репо дає користь лише якщо ви хочете зберігати **Azimutt layout** (позиції таблиць, кольори, saved views) між сесіями — бо AML це і є "project file" Azimutt.

Якщо вам **не потрібен збережений layout** у репо — конвертація в AML надлишкова: просто відкриваєте `npm/er/smart.sql` в Azimutt.

Якщо **хочете зберігати layout** — так, AML у репо має сенс, але тоді його треба редагувати в Azimutt і комітити вручну (layout генерується автоматично лише з перших запусків, а далі зберігає ваші рухи таблиць).

## Мій висновок

Для **CI-генерованого файлу** (автоматично з pg_dump) найпрактичніший варіант — **DBML**, бо:

- Azimutt його їсть (разом з `.sql`)
- SVG можна генерувати без Chromium (`dbml-renderer`)
- Більш портабельний (не lock-in на Azimutt)

Якщо ж хочете Azimutt-first і layout не важливий — **просто лишайте `.sql`** і відкривайте його в Azimutt напряму, без зайвого конверту.
