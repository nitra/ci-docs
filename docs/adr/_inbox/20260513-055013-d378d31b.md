## ADR: `knip.json` — канонічні виключення для Bun-монорепо

**Контекст:** `bunx knip` у проєкті, що повністю відповідає канону `@nitra/cursor`, стабільно показував 9 false-positives (4 unused files, 2 unused devDeps, 3 unlisted binaries). Кожне з них є **наслідком дизайнерських рішень канону** (CLI-only deps через `bunx`/`npx`, test-runner без import-графу, JSON-конфіги поза JS-resolution).

**Рішення/Процедура/Факт:** Створено `knip.json` у корені репо з такими полями:
- `entry` — config-файли, які knip не бачить як entrypoints (`eslint.config.*`, `stylelint.config.*`, `.markdownlint-cli2.*`, `jscpd.config.*`);
- `project` — `**/*.{js,mjs,cjs,...}` щоб `npm/test/**/*.test.mjs` не рахувалися «unused files»;
- `ignoreDependencies` — `["@nitra/cspell-dict", ...]` (резолвляється через `.cspell.json`, а не JS-imports);
- `ignoreBinaries` — `["cspell", "depcheck", "oxfmt", "oxlint", "jscpd", "markdownlint-cli2", "v8r", "shellcheck", "actionlint", "zizmor", "uvx", "git-ai"]` — усі CLI, які канон `n-bun.mdc` забороняє додавати в `devDependencies`.
Також підготовлено промпт (`/n-llm-patch`) для агента в репозиторії `@nitra/cursor`, щоб описані виключення стали офіційним каноном (`knip-canonical.json`) та перевірялися `npx @nitra/cursor check knip`.

**Обґрунтування:** Канон `n-bun.mdc` явно забороняє додавати CLI-only утиліти в `devDependencies` — тому `depcheck`, `oxfmt`, `cspell` справедливо відсутні як npm-пакети, але knip їх не знає. Виключення через `ignoreBinaries` — єдиний спосіб зробити `bunx knip` чистим без порушення канону. `ignoreDependencies` для `@nitra/cspell-dict` — через обмеження knip: він не парсить JSON-конфіги, тільки JS/TS-imports.

**Розглянуті альтернативи:** `rules: { binaries: "off", dependencies: "off" }` — відкинуто, бо вимикає цілі категорії й маскує реальні проблеми; додавання CLI-пакетів у `devDependencies` — порушує `n-bun.mdc`.

**Зачіпає:** `knip.json` (корінь), `package.json` (scripts), `.github/workflows/lint-js.yml` (потенційний `bunx knip` крок); у майбутньому — `node_modules/@nitra/cursor/scripts/utils/knip-canonical.json`, `mdc/js-lint.mdc`.

## ADR: Публікація скоупованого npm-пакету `@nitra/ci-docs` як публічного

**Контекст:** Перший `npm publish` для `@nitra/ci-docs` завершився `E404 Not Found`, а саме поле `publishConfig.access` у `package.json` за замовчуванням відсутнє — npm публікує скоуповані пакети як `restricted (private)`.

**Рішення/Процедура/Факт:** Додано в `npm/package.json`:
```json
"publishConfig": { "access": "public" }
```
Це забезпечує публічну видимість і для локального `npm publish`, і для workflow `JS-DevTools/npm-publish@v4`. Окремо виявлена помилка `npm warn publish "bin[ci-docs]" script name src/cli.mjs was invalid` — для виправлення потрібно переконатися що `src/cli.mjs` починається з shebang `#!/usr/bin/env node` і шлях у `bin` без `./`-префіксу.

**Обґрунтування:** npm за специфікацією розглядає будь-який `@scope/package` як `restricted` без явного `access: "public"`. Помилка `E404` виникає ще до перевірки access — тому корінь проблеми в тому, що org `@nitra` може не існувати на npmjs.com або поточний акаунт не є її членом.

**Розглянуті альтернативи:** Передача `access: public` через CLI-аргумент `npm publish --access public` — не зручно для CI; `publishConfig` у `package.json` — єдине місце правди для обох середовищ.

**Зачіпає:** `npm/package.json` (поле `publishConfig`), `.github/workflows/npm-publish.yml` (параметр `access` у `JS-DevTools/npm-publish`).
